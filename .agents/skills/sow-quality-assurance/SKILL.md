# SOW品質担保スキル

## 目的

ユーザーの曖昧な依頼を、着手前に「ベテランが見てOKと言えるレベルのSOW」に育て、
作業後にそのSOWで検収することで、AI出力の品質を**入口と出口の両方**で担保する。

※「ベテランが見てOK」は目指す水準の説明であり、判定はあくまで④のチェックリストで行う。

---

## 基本原則

- **一人で完成させない**: ユーザーが一人でSOWを完成させようとしない。対話で一緒に育てる。
- **品質基準で判断する**: 質問の回数ではなく、SOWが品質基準を満たしたかで作業開始を判断する。
- **Unknown Unknownを潰す**: ユーザーが気づいていない抜け漏れや矛盾を積極的に指摘する。
- **仮置きで前に進む**: 確定できない項目は無限に質問せず、根拠ある仮置きを明示して進める。
- **作業を止めすぎない**: 品質担保の仕組みは「うっとうしくない」ことが生存条件。
  不要な対話を発生させた時点でこのスキルは失敗している。

---

## ⓪ 適用判断（トリアージ）— 最初に必ず行う

依頼を受けたら、まず以下の3段階のどれに当たるかを判断する。

| モード | 条件 | やること |
|--------|------|----------|
| **省略** | 解釈が一意で、影響が小さく、やり直しが容易（誤字修正・定型作業・単純な質問） | SOWを作らず、そのまま着手する |
| **軽量** | 多少の曖昧さはあるが、やり直しコストが低い | SOW4項目を**1メッセージで提示し、一括確認**する（往復1回を想定）。承認後に着手 |
| **フル** | 曖昧さが大きい／成果物が重い／やり直しコストが高い／既存方針と矛盾しうる（設計・長い実装・対外文書 等） | 以下の①〜⑧を実施する |

迷ったら**軽量**に倒す。軽量で進めた結果、確認の中で曖昧さが大きいと判明したらフルに昇格させる。

---

## フロー（フルモード）

```
① ユーザーの一投を受け取る
② 既存ドキュメント・過去の要件を読み込む
③ SOW初版を生成する（②の内容を反映）
④ 品質チェックを走らせる
⑤ 不足・矛盾を質問で埋める（④⑤を繰り返す。上限あり→「⑤質問のやり方」）
⑥ 完成したSOWをユーザーに提示し、最終確認を取る
⑦ 承認後、SOWをファイルに保存してから作業へ
⑧ 作業完了後、SOWの【完成の定義】と成果物を照合して報告する（検収）
```

---

## ② 既存ドキュメントの読み込み

**全部読まない。今回の依頼に関連するものだけを検索で絞って読む。**

対象の例:
- 要件定義書、仕様書
- 過去のSOW、タスク定義
- README、設計書
- 議事録、意思決定ログ

**目的**: 今回のSOWと過去の方針・決定事項との矛盾を検出するため。
また、ドキュメントを読めば分かることを「要確認」にしないため（質問回数の削減）。

---

## ③ SOW初版の生成

ユーザーの一投＋②で読んだ内容から、以下4項目の骨格を作る。
読み取れない項目は「**要確認**」、推測で埋めた項目は「**仮置き**」と必ず明示し、事実と区別する。

```
【目的・背景】
なぜこの作業が必要か。達成したいゴールは何か。

【完成の定義】
どうなったら作業完了とみなすか。⑧の検収で照合できる粒度で書く。

【スコープ】
やること：
やらないこと：

【制約・前提】
技術的制約、使用ツール、守るべきルール、期限など。
```

---

## ④ 品質チェック

SOWが以下の全項目をクリアしたら「品質基準クリア」と判断する。

### 構造チェック（4項目が存在するか）

- [ ] 目的・背景が書かれているか
- [ ] 完成の定義が書かれているか
- [ ] スコープ（やること・やらないこと）が書かれているか
- [ ] 制約・前提が書かれているか

### 品質チェック（各項目の質）

- [ ] 具体的か（「いい感じに」「適切に」などの曖昧表現がない）
- [ ] 別の解釈が成立しないか（読み手によって意味が変わらない）
- [ ] 完成の定義が検証可能か（⑧で成果物と照合して合否を判断できる）
- [ ] 項目間で矛盾がないか（完成の定義とスコープが食い違っていないか等）
- [ ] 既存ドキュメント・過去の方針と矛盾がないか

**判定例（自己採点のブレを防ぐ）:**
- ❌ 不合格:「エラーを適切に処理する」→ どう処理するか読み手で解釈が割れる
- ✅ 合格:「APIエラー時はリトライ3回、それでも失敗したらログに残してユーザーにエラーメッセージを表示する」

### 矛盾検出の判断基準

既存ドキュメントと今回のSOWを照合し、以下を検出したら必ずユーザーに確認する。

- 以前の方針と今回の方針が異なる → 「前回はAという方針でしたが、今回はBになっています。意図的な変更ですか？」
- 以前と今回でスコープが重複または矛盾している
- 以前決定した制約・前提が今回のSOWに反映されていない

**意図的な変更であれば、その理由をSOWに明記してもらう。**

---

## ⑤ 質問のやり方

品質基準を満たしていない箇所を質問で埋める。

**質問の出し方**
- 不明点が複数ある場合は、**重要度順に並べて選択肢付きでまとめて提示**してよい。
  ユーザーは答えたい分だけ答えればよく、残りは仮置きで埋める。
- 選択肢を出す:「目的はA・B・Cのどれに近いですか？」
- 具体例を求める:「"適切に処理する"とは、具体的にどういう状態ですか？」
- 矛盾は引用して指摘する:「スコープには〇〇とありますが、制約に△△とあり矛盾しています。どちらが正しいですか？」

**やってはいけないこと**
- ゼロから答えさせる（「目的を教えてください」ではなく選択肢を出す）
- 同じ論点を表現を変えて何度も聞く

**ループの脱出条件（重要）**

以下のいずれかに該当したら、質問を打ち切って先に進む。

1. **往復が3回に達した**: 確定しなかった項目は、世間一般・業界標準の感覚で最も妥当な値を
   **仮置きとして明示**した上でSOWに記載し、⑥の最終確認でまとめて承認を取る。
2. **ユーザーが「進めて」「任せる」と明示した**: 品質基準よりユーザーの指示を優先する。
   未確定項目は世間一般の標準的な判断で仮置きし、**仮置き一覧を提示してから**着手する。
   （黙って進めない。何を仮定したかは必ず見えるようにする）
3. **緊急の指示があった**: 上記2と同様に仮置きで即着手し、仮置き一覧は着手報告に添える。

---

## ⑥ 最終確認

品質基準をクリアしたら（または脱出条件で打ち切ったら）、完成したSOWをユーザーに提示して確認を取る。
**仮置き項目は「仮置き」と明示した上で提示する。**

```
以下のSOWで進めてよいですか？

【目的・背景】...
【完成の定義】...
【スコープ】やること：... ／ やらないこと：...
【制約・前提】...
【仮置き】（あれば）...
```

修正があれば④に戻る。承認を得たら⑦へ。

---

## ⑦ SOWの保存と作業中の扱い

- 承認されたSOWを**ファイルに保存する**（例: 作業ディレクトリの `sow.md`、またはプロジェクトの慣習に従った場所）。
  長い作業ではコンテキストが失われるため、ファイルが作業中の唯一の正とする。
- 作業中の判断に迷ったら、SOWに立ち返って判断する。
- 作業中にスコープ外の必要性に気づいたら、作業を止めてSOWを更新し、ユーザーに差分を確認してから再開する。

---

## ⑧ 検収（作業完了後）

作業が終わったら、成果物をSOWの【完成の定義】と1項目ずつ照合し、結果を報告する。

- すべて満たした → 「完成の定義をすべて満たしました」と根拠付きで報告する
- 満たせなかった項目がある → **隠さず明示し**、理由と対応案（追加作業・スコープ調整等）を添える

検収なしで「完了しました」とだけ報告するのは禁止。

---

## よくある落とし穴

| 状況 | 対処 |
|------|------|
| 一投が極端に短い（「〇〇作って」だけ） | SOW初版を作り、「要確認」項目を質問で埋める |
| ユーザーが「なんでもいい」と言う | 「前回はこうでしたがそれでよいですか？」と既存ドキュメントから選択肢を出す。それも無ければ標準的な判断で仮置きし明示する |
| ユーザーが既に仕様書・完成したSOWを持ってきた | ゼロから作らず、④の品質チェックから入る。問題なければそのまま⑥へ |
| 調査・探索タスク（着手前に完成の定義を決められない） | 完成の定義を「何が分かったら調査終了か」（例:「原因が特定でき、再現手順が示せたら終了」）の形で定義する |
| 対話の中でユーザーの回答同士が矛盾した | 既存ドキュメントとの矛盾と同様に、両方を引用して「どちらが正しいですか？」と確認する |
| 既存ドキュメントが見当たらない | 矛盾チェックをスキップし、構造・品質チェックのみ実施する |
| 作業中にスコープ外の必要性に気づく | 作業を止め、SOWを更新してユーザーに再確認を取る（⑦参照） |
| 「急ぎで」と言われた | ⑤の脱出条件3に従い、仮置き一覧を添えて即着手する |
