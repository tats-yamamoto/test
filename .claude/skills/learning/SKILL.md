# 学習・パターン記録スキル

## データの場所

- 学習パターン: `.ai-secretary/global/patterns.json`
- タスクデータ: `.ai-secretary/projects/<PJ>/tasks.json`
- 関係者データ: `.ai-secretary/projects/<PJ>/people.md` および `.ai-secretary/global/people.md`

## 1. タスク完了時の記録（task-managerから呼ばれる）

タスクを完了（done）にしたら必ず実行:

1. 所要日数を計算（created_at → completed_at の差分）
2. `patterns.json` の `time_estimation.accuracy_log` に記録:
   ```json
   { "task_id": "...", "title": "...", "category": "...", "created_at": "YYYY-MM-DD", "completed_at": "YYYY-MM-DD", "days": N }
   ```
3. マイルストーンがある場合、各段階の所要日数も `accuracy_log` に個別記録
4. 同種タスク（同じカテゴリ・類似タイトル）のパターンがあれば `task_decomposition` を更新
5. マイルストーンの実績を `planning_history.observations` にも記録
6. patterns.json 保存後に読み直して構文確認

## 2. タスク取り下げ時の記録（task-managerから呼ばれる）

タスクを drop したら必ず実行:

1. `patterns.json` の `dropped_task_patterns.observations` に特徴を追記
   - 例: 「チャットで拾ったタスクで2週間以上催促がなかったもの」
   - 例: 「依頼者不明で優先度が上がらなかったもの」
2. patterns.json 保存後に読み直して構文確認

## 3. レビューFB記録

レビューフィードバックを受けたら実行:

1. tasks.json の該当タスクの `review_history` にFB内容を追加:
   ```json
   { "reviewer": "レビュアー名", "date": "YYYY-MM-DD", "feedback": "FB内容", "resolved": false }
   ```
2. 該当PJの `people.md` にレビュアーの傾向を追記（日付必須）
   - 例: 「2026-03-28: 結論ファーストを求める指摘 → 結論ファースト重視の傾向」
3. `global/people.md` の該当者にも全般的な傾向として反映
4. `patterns.json` の `review_tendencies.by_reviewer` に定量データを更新:
   ```json
   { "<レビュアー名>": { "total_reviews": N, "common_points": ["構成", "数字の根拠"], "last_review": "YYYY-MM-DD" } }
   ```
5. 保存後に構文確認
6. 傾向の分析をユーザーに共有:
   - 過去のFBと比較して一貫した傾向があれば伝える
   - 例: 「この方は3回連続で構成の指摘をしています。次回は構成を先に見せると良いかもしれません」

## 4. ユーザーが提案を修正した場合

秘書の提案（優先度、カテゴリ推定、段取り等）をユーザーが修正した場合:

1. `patterns.json` の `priority_tendencies.observations` に修正内容を追記:
   ```json
   { "date": "YYYY-MM-DD", "original": "...", "corrected": "...", "context": "..." }
   ```
2. 傾向を言語化して記録（次回の同種提案で反映するため）
3. patterns.json 保存後に構文確認

## 5. 繰り返しタスクの検出

同名・類似タイトルのタスクが定期的に発生していることを検出したら:

1. `patterns.json` の `recurring_tasks` に記録
2. 次回の発生時期が近づいたら「そろそろこれやりませんか？」と提案

## 6. 学習状況の確認

ユーザーから学習状況を問われた場合:

- **概要表示**: タスク完了記録件数、FB記録件数、検出パターン数等
- **パターン詳細**: タスク分解パターン、見積もり精度、レビュアー傾向等
- **改善提案**: 「報告書作成は想定より1日多めにバッファを取りましょう」等
- 誤った学習を見つけた場合、ユーザーが手動で修正できるよう案内する

## 7. 暗黙観察の記録

会話中にユーザーの暗黙的な好み・傾向が現れた場合に記録する。core-principles の「暗黙観察」ルールに基づき、全エージェントがこの手順を呼び出す。

### 記録すべき場面

- ユーザーが秘書の提案を**修正**した（優先度の入れ替え、文言の書き換え、段取りの変更 等）
- ユーザーが複数の選択肢から**選択**した（consultant の提案、ドラフトの方向性 等）
- ユーザーが秘書の提案を**却下**した（「それは要らない」「そうじゃなくて」等）
- ユーザーが**繰り返し同じ指示**をした（毎回「結論を先に」と言う 等）
- ユーザーの**ワークフローのパターン**が見えた（毎朝最初にやること、特定の順序 等）
- 会話中にPJ・関係者に関する**暗黙知**が出てきた（人の傾向、暗黙のルール、力関係の変化、PJの雰囲気 等）— core-principles「会話からの情報収集」の蓄積型に該当するもの

### 記録しなくてよい場面

- 単なる事実の訂正（日付の間違い、名前の間違い等） — これはバグ修正であり好みではない
- 明示的に「こうして」と指示した内容で、既にスキル・ルールに反映済みのもの
- 1回きりの文脈依存の判断（今回だけ特別な事情があった等）

### 記録フォーマット

`patterns.json` の `observations` 配列に追記する:

```json
{
  "id": "obs-YYYYMMDD-NNN",
  "date": "YYYY-MM-DD",
  "source": "スキル名またはエージェント名（drafter, consultant, task-manager 等）",
  "type": "correction | preference | decision | workflow",
  "description": "何が起きたかの簡潔な記述",
  "context": "どういう状況で起きたか（PJ名、タスク名、会話の流れ等）"
}
```

**type の使い分け:**
- `correction`: 秘書の提案をユーザーが修正した
- `preference`: ユーザーの好み・スタイルが現れた
- `decision`: 複数選択肢からの選択
- `workflow`: 作業手順・順序のパターン
- `knowledge`: PJ・関係者に関する暗黙知（人の傾向、暗黙のルール、力関係の変化等）

### 記録の手順

1. 上記の「記録すべき場面」に該当するか判断する
2. 該当する場合、`patterns.json` を読み込む
3. `observations` 配列に新しいエントリを追記（IDは `obs-YYYYMMDD-NNN` で採番）
4. 保存後に構文確認
5. **ユーザーには記録したことを伝えない**（暗黙的に行う。ただし学習状況を聞かれたら開示する）

### 既存の明示的学習との関係

- セクション1〜5の明示的学習（タスク完了記録、レビューFB等）は**そのまま継続**する
- 暗黙観察は、明示的学習では拾えない「行間の好み」を補完するもの
- 同じ出来事が明示的学習と暗黙観察の両方に該当する場合、明示的学習を優先し、観察は不要

## 8. パターン検出（観察 → 気づき）

蓄積された観察からパターンを検出し、信頼度スコア付きの「気づき（insight）」に昇華する。

### 実行タイミング

- 朝ブリーフィング時に自動実行（未処理の観察が**5件以上**ある場合のみ）
- ユーザーから「学習状況を見せて」と言われた場合
- ユーザーから明示的に「パターン検出して」と言われた場合

### 検出手順

1. `patterns.json` の `observations` を読み込む
2. 以下の観点でクラスタリングする:
   - **同種の修正が繰り返されている**: 例「ドラフトで3回連続で結論を冒頭に移動している」
   - **同じ type の観察が集中している**: 例「correction タイプが drafting 関連で5件」
   - **同じ source からの観察が多い**: 例「prioritization からの correction が4件」
   - **類似の description を持つ観察**: 例「期限の見積もりを常に前倒しに修正」
3. クラスタが見つかったら、`insights` 配列に気づきを記録する（既存の insight と重複する場合は更新）

### insight のフォーマット

```json
{
  "id": "ins-YYYYMMDD-NNN",
  "created_at": "YYYY-MM-DD",
  "updated_at": "YYYY-MM-DD",
  "confidence": 0.3,
  "description": "気づきの内容（行動パターンを言語化したもの）",
  "evidence": ["obs-YYYYMMDD-NNN", "obs-YYYYMMDD-NNN"],
  "domain": "ドメイン（drafting, prioritization, planning, communication, workflow, scheduling 等）",
  "status": "active | crystallized | dismissed"
}
```

### 信頼度スコアの管理

| 条件 | スコア変動 |
|---|---|
| 初検出（観察2〜3件の一致） | 0.3（新規作成） |
| 追加の観察で同パターン確認 | +0.1〜0.2（最大0.9） |
| 矛盾する観察が出た | −0.2 |
| 1ヶ月以上新しい根拠なし | −0.1（自然減衰） |
| ユーザーが明示的に否定 | 0.0（status → dismissed） |

### 処理済み観察のアーカイブ

- insight に取り込まれた観察（evidence に含まれるもの）は `observations` 配列から削除する
- insight に取り込まれなかった古い観察（30日以上前）も削除する
- これにより `observations` 配列の肥大化を防ぐ

## 9. 結晶化提案（気づき → スキル・ルール・エージェントへの反映）

高信頼度の気づきが蓄積したら、システム自体の改善をユーザーに提案する。

### 結晶化の条件

以下の**両方**を満たすとき、結晶化提案を生成する:

1. **信頼度 0.7 以上**の insight が存在する
2. **同じ domain の insight が 3件以上**集まっている（または単独でも信頼度 0.9 の insight）

### 提案の種類

| 気づきの domain | 提案先 | 例 |
|---|---|---|
| drafting | テンプレート更新、weekly-report スキル修正 | 「デフォルトの文体を結論ファーストに変更しませんか？」 |
| prioritization | prioritization スキルのルール追加 | 「○○PJのタスクを常に高優先にするルールを追加しませんか？」 |
| planning | planning スキルのバッファ設定 | 「報告書タスクの見積もりに+1日バッファを標準にしませんか？」 |
| communication | people.md の更新、ドラフトテンプレート | 「○○さんへのメールは常にCC付きにするルールを追加しませんか？」 |
| workflow | 新スキル作成、ルール追加 | 「毎週金曜の作業パターンをスキル化しませんか？」 |
| scheduling | meeting スキルの調整、user-profile 更新 | 「午前中はブロックする運用をルール化しませんか？」 |
| knowledge | knowledge.md / people.md の追記 | 「○○さんの傾向として〜を people.md に追記しませんか？」 |
| 複数domain横断 | 新サブエージェント提案、CLAUDE.md 更新 | 「○○専用のワークフローをエージェントとして切り出しませんか？」 |

### 提案の手順

1. 結晶化条件を満たす insight クラスタを特定する
2. クラスタの内容から、どのファイルをどう変更すべきか具体案を作成する
3. 朝ブリーフィングの「秘書からの提案」セクション、またはユーザーが学習状況を確認した際に提示する:

```
💡 学習からの提案（結晶化）

以下のパターンが高い確信度で検出されました:

1. [confidence: 0.8] ドラフトでは常に結論ファーストを好む（根拠: 5件の修正観察）
2. [confidence: 0.7] 報告書の見積もりは実績より1日多い（根拠: 3件の完了記録）
3. [confidence: 0.7] ○○さんへの連絡は丁寧語を強めに（根拠: 3件の文体修正）

提案:
- weekly-report スキルに「結論ファースト」をデフォルトルールとして追加
- planning スキルの報告書カテゴリに +1日バッファを標準設定

反映しますか？（個別に選択可能）
```

4. ユーザーが承認した提案のみ実行する
5. 実行後、該当 insight の status を `crystallized` に更新する
6. **スキル・ルールを変更した場合は impact-check スキル（EVENT: スキル変更）を実行する**

### 結晶化の原則

- **具体的に提案する**: 「改善しませんか？」ではなく「このファイルのこの部分をこう変えませんか？」
- **根拠を示す**: どの観察・気づきに基づく提案かを明示する
- **選択可能にする**: 複数提案がある場合、個別に承認/却下できるようにする
- **小さく変える**: 1回の結晶化で大きな構造変更はしない。ルール1行追加、テンプレート微修正レベル
- **提案頻度を制限する**: 同じ domain の提案は週1回まで。毎朝提案が出ると鬱陶しい
