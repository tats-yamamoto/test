# 朝のブリーフィング生成スキル

## 生成手順

### 0. 現在時刻の確認

`date` コマンドで今日の日付・曜日・時刻を確認する。

### 0.5. 週次スケジュールの整合性チェック（自動リセット）

`weekly-schedule.json` を読み込み、`week` フィールドが**今日の属する ISO 週番号**と一致するか確認する。

- **一致しない場合**: 会議管理スキルの「5. 週次リセット」手順を自動実行し、`weekly-schedule.json` を今週分で再生成する。ただし、前週の `weekly-schedule.json` に `source_id: null`（単発会議）かつ日付が今週に含まれるエントリがあれば引き継ぐ。
- **一致する場合**: そのまま次のステップへ進む。

これにより、月曜朝に週次リセットが呼ばれなかった場合でも、最初のブリーフィング時に自動補完される。

### 1. データ読み込み

以下のデータをすべて読み込んでください:

- `.ai-secretary/global/user-profile.md` — 今日の曜日が勤務日か、ブロック日か、定例会議があるか
- `.ai-secretary/global/patterns.json` — 繰り返しタスク、作業傾向
- `.ai-secretary/global/reminders.json` — 秘書のアクションキュー（リマインダー）
- 全PJの `tasks.json` — 全タスクの期限・ステータス
- 全PJの `daily/tasks.json`, `weekly/tasks.json`, `monthly/tasks.json` — 定期タスク
- `.ai-secretary/global/weekly-schedule.json` — 今週の会議スケジュール
- 全PJの `knowledge.md` — PJの現在地（必要に応じて参照）

### 2. ブリーフィング構成

以下の順序で情報を提示してください:

#### リマインダー処理（最初に実行）

`reminders.json` を読み、`trigger_date <= 今日` かつ `done == false` のものを処理する:

- **`add_to_schedule`**: `details` の内容を `weekly-schedule.json` に追加する
- **`notify_user`**: ブリーフィング内の「アラート」セクションに `details.message` を表示する
- **`check_and_notify`**: `details` に記載された確認を行い、結果をユーザーに報告する

処理したリマインダーは `done: true` に更新し、`reminders.json` を保存する。
※ リマインダーの処理結果はブリーフィング内で自然に報告する（「リマインダーにより追加しました」等の機械的な表示は不要）

#### 今日の定期タスク

定期タスクの完了判定には `completion_log` を使用する。**重要: 週次・月次タスクの `period` は「成果物の提出先サイクル」を表す（例: 週報のW15 = W15月曜の報告会で発表する分）。今の作業週/月ではなく、次の提出先サイクルを基準に判定すること。**

- **日次**: 今日の日付（YYYY-MM-DD）が completion_log に存在するか確認。なければ未完了として表示
- **週次**: `cycle_day`（サイクルの基準曜日）から対象periodを特定する:
  1. 今日が `cycle_day` と同じ曜日 → 対象period = 今日のISO週番号
  2. それ以外 → 対象period = **次の `cycle_day` の日付**が属するISO週番号
  3. `cycle_day` が未設定 → 対象period = 今週のISO週番号（従来互換）
  - 対象periodが completion_log に存在するか確認。なければ未完了として表示
  - 締切ルール（deadline_rule）に基づいて実際の締切日も表示する
  - 例: 今日が木曜(W14)、cycle_day=mon → 次の月曜=4/6(W15) → W15をチェック
- **月次**: `cycle_date`（サイクルの基準日）から対象periodを特定する:
  1. `cycle_date` が `"last"` または 今日の日 <= `cycle_date` → 対象period = 今月（YYYY-MM）
  2. 今日の日 > `cycle_date` → 対象period = 来月（YYYY-MM）
  3. `cycle_date` が未設定 → 対象period = 今月（従来互換）
  - 対象periodが completion_log に存在するか確認。なければ未完了として表示
  - 月末が近い場合（残り5営業日以内）は特にリマインド

表示形式:
- 完了済みの定期タスクは「✅ 済」と表示（安心感のため）
- 未完了の定期タスクは「⬜ 未」と表示し、対応を促す
- 日次タスク → 週次タスク → 月次タスクの順で表示

#### スケジュール概要
- 今日の曜日、勤務日/ブロック日
- 今日の会議（weekly-schedule.json から、status が scheduled のもの）
  - 会議の目的（purpose）・準備物（prep）があればそれも表示
  - 関連タスクとの紐づけを提案（会議のPJ・参加者から推測）
- 会議の隙間時間の見通し（長い隙間=重め作業可、短い隙間=軽め作業向き）

#### 今日やるべきタスクの提案（優先順位付き）

prioritization スキルの判断基準に従い、以下の優先度で提示する:

- 🔴 今日が期限（hard）のタスク
- 🟠 3日以内に期限が来るタスク
- 🟡 進行中のタスク（次のアクションを明示）
- 🔵 asapタスク（他との優先度を比較して提案）

各タスクに対して:
- なぜ今日やるべきかの根拠
- どの隙間時間（重め/軽め）に入れるかの提案

**表示ルール:**
- todos があるタスクは進捗 `TODO [完了数/全数]` を表示し、未完了TODOを `└ TODO:` で表示
- milestones があるタスクは直近の未完了マイルストーンを `└ MS:` で表示
- related_meetings があるタスクは直近の未来の会議を `└ 会議:` で表示
```
t-20260401-002 | 賞与考課 | todo | 4/17 | TODO [4/5]
  └ MS: 面談完了(4/14)
  └ 会議: 賞与考課 面談(4/14)
```

#### 会議の事後フォロー

`weekly-schedule.json` から**昨日の会議**（status が scheduled または rescheduled）を抽出し、各会議について:

- 「〇〇（会議名）の結果、新しいタスクや対応事項はありますか？」とフォローする
- タスクの `related_meetings` に該当する会議がある場合は、そのタスクと紐づけて表示:
  - 「賞与考課の面談が昨日ありました。FBによる修正は必要ですか？不要なら完了にできます」
- 会議から抽出すべき情報（VTT・メモ等）があれば extractor の利用を提案する

※ 今日の会議については事後フォロー不要（まだ終わっていない可能性がある）。翌朝のブリーフィングでフォローする。

#### アラート
- 期限切れのタスク
- waiting状態が長い（5日以上）タスク → 「フォローしますか？」
- 繰り返しタスクの発生時期が近い場合
- starts_at（着手可能日）が1週間以内に到来するタスク → 「もうすぐ着手可能になります」とリマインド。related_meetings がある場合は「〇〇（会議名）の後にアクティブになります」と表示

#### 秘書からの提案
- 「やらなくてもよさそう」なタスクの指摘（2週間以上放置、催促なし等）
- 「そろそろこれに着手しませんか？」（期限までの逆算から。planning スキルの段取り提案と連動）
- パターンに基づく助言（「このタイプのタスクは想定より1日多くかかる傾向があります」等）

#### パターン検出 & 結晶化チェック（学習の自動進化）

`patterns.json` の `observations` と `insights` を使って、学習の進化を自動チェックする。

**Step 0: ナレッジ更新提案**（type: knowledge の未処理観察がある場合）

`observations` に `type: "knowledge"` のエントリがあれば、knowledge-base スキルの「蓄積されたナレッジ観察からの更新提案」手順を実行する。ナレッジは鮮度が重要なので、パターン検出より先に処理する。

**Step 1: パターン検出**（未処理の観察が5件以上ある場合のみ実行）

learning スキルのセクション8（パターン検出）を実行する:
1. `observations` を読み込み、類似パターンをクラスタリング
2. クラスタが見つかれば `insights` に気づきを記録（新規作成 or 既存の信頼度更新）
3. insight に取り込まれた観察は `observations` から削除する
4. 30日以上前のパターン化されなかった観察も削除する

**Step 2: 結晶化チェック**（週1回程度。前回から7日以上経過した場合のみ）

learning スキルのセクション9（結晶化提案）の条件を確認する:
- 信頼度 0.7 以上の insight が存在するか
- 同じ domain の insight が 3件以上集まっているか（または単独で信頼度 0.9）

条件を満たす場合、「秘書からの提案」セクション内に結晶化提案を表示する:
```
💡 学習からの提案
- [確信度: 0.8] 〜の傾向を検出（根拠: N件の観察）
  → 提案: 〜スキルに〜ルールを追加
  反映しますか？
```

条件を満たさない場合、このセクションは表示しない（毎朝出ると鬱陶しいため）。

### 3. 出力のトーン

- 秘書として簡潔かつ親しみやすく
- 一覧の羅列ではなく「今日はこう進めてはどうですか？」という提案型
- ユーザーの作業傾向（user-profile.md の work_style）を踏まえたアドバイス
