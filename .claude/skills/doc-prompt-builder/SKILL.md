# 資料プロンプト生成スキル（Claude Design 向け）

ClaudeCode 側で「資料に書くべき内容と構成」を作り込み、**Claude Design に貼る1個のプロンプト**にまとめる。
デザイン（配色・フォント・レイアウト）は Claude Design 側の**常駐デザインシステム**に委ねるため、**プロンプトにデザイン指示は含めない**。

## 全体の位置づけ

```
doc-pattern-extraction → global/review/資料作成/（構造テンプレ）
                                   │
ユーザー指示＋素材 ──────────────┤  ← 本スキルが合成
                                   ▼
                  骨子（スライド構成案＋確信度）
                                   │
                                   ▼  ← ★ユーザーと骨子レビュー（往復・必須）
                       Claude Design 用プロンプト（1個）
                                   │
                                   ▼  ← Claude Design が常駐デザインシステムで作図
                                 pptx
```

## drafting との棲み分け

- **drafting**: 文章主体の成果物（メール／議事録／文章の報告書）をチャットに出力。
- **本スキル**: pptx 資料を Claude Design で作るための**プロンプト**を出力（スライド単位の構成＋内容＋図表指示）。
- 内容ドラフトの作り込み自体は drafting の流儀（背景・ナレッジ・宛先の好みを踏まえる）を流用する。

## 入力（ヒアリング）

不足していれば確認する:

- **種別**: 報告 / 提案・決裁 / 新規事業（企画書・実証実験計画書・事業計画） ※不明なら素材から判定して確認
- **テーマ**（何の資料か）
- **提出先**（誰に）と **提出形態**（社外 / 社内）
- **盛り込む素材**: VTT・メモ・既存タスク・前回資料・数字 など

## 参照（必ず読む）

1. 該当構造テンプレ: `.ai-secretary/global/review/資料作成/{報告|提案・決裁|新規事業}-構造.md`
2. `共通基盤-構造.md` ＋ `図表パターン.md`
3. PJナレッジ `knowledge.md` / 関係者 `people.md` / レビュー傾向 `global/review/people/<提出先>.md`
4. タスク背景 `tasks.json` の `context`
5. 所属・部署名 `global/user-profile.md`（表紙・宛先の補完用）
6. **資料の核となる概念・フレーム・展開シナリオが特定の会議に由来する場合、その会議の一次情報（VTT/txt 原文）を読む。** knowledge.md の要約だけに頼らない。
   - 理由: 要約は「結論」を残し、「なぜそう言えるのか（前提・論理）」を落としがち。資料を自己完結させるには、その概念を生んだ発言の文脈・理由を押さえる必要がある（点→線→面のように、結論だけ書くと読者がわからない事故が起きる）
   - 該当会議の特定: knowledge.md の決定事項・FB履歴に日付があれば、その日付の `meetings/` 配下を読む

## 手順

1. **種別判定** → 使う構造テンプレを選ぶ
2. **構成の骨格**をテンプレのスライドフローから作り、素材を各スライドへ割り付ける
3. **スライドごとに「骨子（スライド構成案）」を作る**: 各スライド＝【メッセージライン（主張1文）＋ 要点（内容ドラフト）＋ 図表型 ＋ 確信度】
   ※ ここでいう「骨子」は**ユーザーとレビューするスライド構成案**。プロンプト内の「骨子セクション（Claude Design内部指示）」とは別物。
   - メッセージライン: テンプレの「メッセージライン例」の型に沿う
   - 内容: 素材＋ナレッジから具体化（draftingの作り込み）
   - 図表: `図表パターン.md` から該当型を指定（軸・要素・範囲明示まで）。**既存の前回資料（pptx等）に流用できる図があれば流用を優先**（毎回ゼロから作図させない。Claude Designには「ここに既存○○図を配置」とプレースホルダ指定）
   - **確信度（必須）**: 各スライドの主要な主張に **①合意済み**（議事録で確認できる）／**②仮説**（方向は出したが未検証）／**③未確定**（これから聞いて決める）のいずれかをたたきで付す。**自分の推測を勝手に①にしない**。判別できないものは次の骨子レビューでユーザーに確認する
4. **自己完結性チェック（必須・初見の読者シミュレーション）**: スライドを S1 から順に「予備知識ゼロの読者」になったつもりで通読し、各スライドが単体で意味を成すか確認する。**用語だけでなく「論理・前提」もチェックする**（今回の最大の学び）。
   - **(a) 未定義の概念・造語・略語**: 初出スライドで説明なく使われていないか
     - ❌ NG: 「骨子」「全スライドルール」セクションに定義を書くだけ — Claude Design が内部で理解しても聴衆には見えない
     - ✅ OK: 初出スライドの本文・図表指示に一言説明を入れる（括弧書き・図中ラベル等）
   - **(b) 前提・論理の飛躍（用語より重要）**: フレーム・段階・結論を「なぜそう言えるか」抜きで提示していないか
     - 例: 「点→線→面」「B2B先行」のような展開シナリオは、用語を訳すだけでは伝わらない。**「なぜ一気にやらないのか／なぜその順なのか」という理由**を、それが効く最初のスライドに置く
     - チェック観点: そのスライドだけ見せられた人が「なぜ？」と思う主張がないか。あれば理由を一言補う or 理由を語る前段スライドへの参照を付ける
   - 判断基準（本文 / Appendix の振り分け）:
     - 事業フレームの核（フェーズ名・展開段階名・独自造語）とその**論理** → 本文で必ず説明（Appendixだけでは不十分）
     - 詳細技術用語・製品名・プロトコル名 → Appendixへの記載でも可。**ただし「全部Appendix」にしない** — 資料の主役になる固有名（実証の相手役など）は本文初出で一言
     - 提出先が自ら発案した用語でも → 後で第三者が読む場合を想定し、初出で短い確認説明を入れる
   - **根本原則: 「骨子に書いた = 説明した」ではない。聴衆が見るスライド本文で、用語も論理も自己完結していることが前提**
5. **コンテンツ密度の確認（重要）**: 各スライドの内容量を見て、16pt本文で1枚に自然に収まるか判断する。
   - 箇条書きが5〜6行を超える、長い文章が3段以上続く、などは過密の兆候
   - 過密なら Claude Design に渡す**前に**ユーザーへ提案する: 「このスライドは分割しますか？」「この箇条書きを3点に絞りますか？」
   - 機械的な文字数制限ではなく、「16ptで読みやすいか」という設計判断
   - **手法ローテ（連続スライドで同じ図形式を続けない）**: 隣接スライドが両方とも番号リスト①②③等にならないよう、表/フロー/パネル/既存図流用 等で変化をつける（レイアウト・図版規定.md §4.8）。同じ三つ組でも"並列の価値"はリスト、"処理の流れ"はフロー、と形を変える
6. **トーン調整**: 報告=事実＋所感／社外提案=訴求・コスト低減／社内決裁=投資の正当性
7. **先回り**: 提出先のレビュー傾向があれば反映（self-review の考え方）
8. **骨子レビュー（ユーザーと・必須。本スキルの肝）**: 完成プロンプトを出す**前に**、骨子（スライド一覧＝各スライドのメッセージライン＋要点＋図表型＋確信度）を**ユーザーとスライド単位でレビューする**。いきなり全スライドの完成文を作らない。「各スライド、これでいいか？」を必ず確認し、以下を一緒に決める/直す:
   - **進め方＝1枚ずつ、実際の内容を見せてレビュー**（一覧表で一気に確認では判断できない＝「内容を見ないと分からん」。1枚提示→OK→次、で進める）。確信度の見せ方もスライド単位で都度すり合わせる（メニューを並べて先に決めようとしない）
   - **中身・切り口・抜け**: そのスライドの主張・要点・順序でよいか。落ちている観点・余分な観点はないか
   - **確信度の確定**: 私が付けた ①合意/②仮説/③未確定 のたたきをユーザーに確認・修正してもらう。**「決まっていないのに決まったように書く」を防ぐ最重要ポイント**。検討段階の新規事業ほど②③が多い前提で臨む
   - **未確定（③）の扱い**: 本文に書ける段階か、それとも「〇〇ヒアリング後に確定」と**空けておく**か（埋めずに残すのも誠実な選択）
   - **確信度の見せ方（このデッキでどうするか）**: 書き分けの方法を**この場でデッキごとに決める**（固定ルールにしない）。例: (a)トーンで書き分け〔①断定／②仮説の語り口／③空けて明示〕、(b)確信度ラベルを明示、(c)両方
   - ※ 大型デッキは特に「骨子で方向を合わせてから展開」を徹底（obs-20260529-006）
9. **書き分けて本体プロンプトに展開**: 骨子レビューで確定した確信度・方針に従い、①は断定／②は仮説トーン／③は空けて明示で各スライドを記述し、下記テンプレートで**コピペ可能な1ブロック**を出力
10. ユーザーが修正したら反映（往復）。修正内容は learning（`observations`, source: `doc-prompt-builder`）に記録
11. **出力pptxの標準準拠チェック（納品前・必須）**: Claude Design が生成した pptx、またはスクリプト（python-pptx）で組んだ pptx が手元に来たら、納品前に必ず検証する。**プロンプトに文字サイズを厳守指定しても、生成側（Claude Design／スクリプト）が守るとは限らない**（"標準があるのに出力が裏切る"。v5 で OFF_SCALE 263箇所＝obs-20260602-001）。
    - 実行: `python .ai-secretary/global/review/資料作成/pptx_font_audit.py <file.pptx>` → **判定 PASS（OFF_SCALE=0 / TOO_SMALL=0）** を確認
    - FAIL なら `pptx_render.py` で PNG 化して目視し、**文字を縮めず**「文言を削る／コンテナを広げる／スライドを分ける」で直す（本文14pt未満禁止）
    - 手順の詳細は `self-review` の「3.5 pptx成果物の標準準拠チェック」を参照

## 出力するプロンプトのテンプレート

> 下記をコードブロックで、そのまま Claude Design に貼れる形で出力する。`<>` は埋める。デザイン指示は書かない。

```
あなたは<部署（user-profileから）>の資料作成を支援するデザイナーです。
常駐のデザインシステムに従い、以下の構成・内容で pptx スライドを作成してください。

## 文字サイズ（厳守・変更禁止）
| 要素 | サイズ | 備考 |
|---|---|---|
| スライドタイトル（話題ラベル） | 20pt Gray Bold | |
| メッセージライン（主張1文） | 18pt Bold Black | テキスト配置: CENTER（中央揃え）|
| スライド内見出し | 18pt Bold | |
| 本文・箇条書き | **16pt**（密なら14pt） | **14pt未満禁止** |
| 表セル・図ラベル・キャプション | 11〜12pt | ここだけ小さくしてよい |
| フッター | 10pt | |
**重要（文字サイズ厳守）: 指定サイズで内容が収まらない場合、文字を縮小することは禁止。文言を削る・スライドを分ける・レイアウトを変えるなど、内容と設計を見直すこと。**

## レイアウト
- 各スライド上部に「メッセージライン（主張1文）」を置く。レイアウト・余白はデザインシステムに準拠。

## 色の役割（厳守・この割り当て以外で色を使わない）
- 基調: 黒（本文）・グレー（補足/基盤/他社/前段階）・白（背景）。
- 主アクセント=オレンジ: 自社・主役・強調・今フォーカスする要素（差し色なので多用しない）。
- 副アクセント=ティール（オレンジの補色）: 注記、または対比概念の一方（B2B↔B2C 等）。
- 赤=リスク/必達ラインのみ。緑=達成/成功ノードのみ。青=体制図など多カテゴリ分類のみ。
- **アクセントは1スライド2〜3色まで**。「点→線→面」「Phase」等の進行段階は色を増やさず、**グレー（初期/基盤）→オレンジ（自社が広げる範囲）の濃淡**で表す（段階ごとに別色を割り当てない）。

## 全体ルール（必読）
- 専門用語・造語・コンセプト語はすべて初出スライドで一言説明を添える（括弧書き・図中ラベル等）。詳細技術用語はAppendixでも可。事業フレームの核となる造語・フェーズ名は本文で説明すること。
- 自社（<会社名>）の担当範囲・提供範囲は図中に明示する。
- **確信度の誠実な区別（厳守）**: 「決まったこと」と「仮説・これから確かめること」を読者が区別できるようにする。区別の方法は骨子レビューでデッキごとに決め、それに従う（例: ②③を仮説トーンで書き分ける／本文は断定で書き「未確認」注記を被せる）。**未確定を勝手に確定させない**。
- **未確認/要検討の注記は"レイアウト非干渉のフローティング付箋"**（レイアウト・図版規定.md §4.8）: 該当箇所の上にやや雑に重ねるだけ。枠・余白を確保せず、コンテンツブロックにしない（消しても本体レイアウトが動かない）。絵文字は使わずテキスト＋四角い図形。
- 締めは「以上」、補足は「Appendix／（ご参考）」。
- **わかりやすさの自律判断**: 上記の構成・内容に忠実に従いつつ、読者の理解を助けるために必要と判断した場合は、補足の一言・表現の言い換え・注記の追加を自分で加えてよい。ただし `🔎要検討` は消さないこと。構成（スライド枚数・順序）は変えない。

- テーマ: <>
- 提出先: <>（<社外 / 社内>）
- トーン: <報告=事実＋所感 / 社外提案=訴求 / 社内決裁=正当性 など>

# スライド構成と内容
## S1 表紙
- タイトル: <テーマ＋"状況/報告/提案/決裁説明"> ／ 日付 ／ 部署 ／ 作成者
## S2 <役割（趣旨/目次・ご提案概要 等）>
- メッセージライン: <主張1文>
- 内容: <箇条書き or 文>
- 図表: <図表型（あれば）>
## S3 ...
（テンプレのフローに沿って続ける。報告は末尾に必ず ★所感/課題/学び）

- S<n>: <図表型: 大日程ガント/体制図/工数・費用表/リスク表/調整サマリー/ポジショニングマップ/概念図>
  - <軸・要素・「ご提案/ご報告範囲」明示・▼マイルストーン 等>
```

## 注意

- **文字サイズと色の役割は例外として明示する**（プロンプトに上記テーブル＋色の役割を必ず含める）。レイアウト・余白はデザインシステムに委ねるが、サイズと色は Claude Design が勝手に決めると横山一スタイルから外れる（半端なpt、意味のない緑・青の多用）ため、明示指定が必要。配色ルールの一次ソースは `レイアウト・図版規定.md §5`。
- 種別ごとの構成・トーン・図表は必ず構造テンプレに準拠する（テンプレが一次ソース）。
- 1件依存の種別（事業計画）はテンプレが薄いので、構成は慎重にし、内容で補う。
- **凝縮・フラット優先**（ins-20260529-001）。内容ドラフトを冗長にしない。
- 往復前提のため**メインで実行**（サブエージェントに切り出さない）。
- 固有名（PJ名・組織名）はプロンプトに焼き付けず、その都度ヒアリング／user-profile から補完する。
- **「骨子」の2つの意味を混同しない**: (1) ステップ3〜8でユーザーとレビューする**スライド構成案**＝「骨子（スライド構成案）」。(2) プロンプト内の「**骨子セクション**」＝Claude Design への内部指示。プロンプト内のセクションに定義を書くだけでは聴衆への説明にならない（ステップ4で必ず確認）。
- **骨子レビューを飛ばさない（今回の最大の学び）**: 完成プロンプトをいきなり出さず、必ずステップ8でユーザーと骨子をレビューしてから展開する。私が一気に全スライドを埋めると、検討段階の未確定事項まで"決定事項の顔"で書いてしまう事故が起きる（obs-20260601系）。
- **`🔎要検討` と 確信度 は別物**: `🔎要検討`＝"足りない情報（gap）"を欄外に示す注記。確信度＝本文の主張が①合意/②仮説/③未確定のどれか。**本文を断定で書いて🔎で補う、では不十分**（本文の主張自体が②③なら、本文を仮説トーン／空けにする）。
- **Claude Design への編集裁量**: プロンプトに「わかりやすさの自律判断」ルールを含め、機械的な実行にとどまらず読者の理解を助ける補足を自律的に加えられるようにする（上記テンプレートの全体ルール参照）。
